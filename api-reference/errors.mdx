## Envelope

All errors follow OpenAI's format:

```json
{
  "error": {
    "message": "Human-readable description",
    "type": "invalid_request_error",
    "code": "file_too_large",
    "param": "file"
  }
}
```

The body is always valid JSON. `param` is included when the error relates to a specific field.

## Types

| `type` | HTTP | Meaning |
| --- | --- | --- |
| `invalid_request_error` | 400 / 413 | Bad input, quota exceeded, unsupported format |
| `invalid_request_error` with `code: model_not_found` | 404 | Model slug doesn't exist or isn't available on your plan |
| `auth_error` | 401 | Missing or invalid API key |
| `rate_limit_error` | 429 | Per-key or per-IP rate limit hit |
| `quota_exceeded` | 403 | A plan-level quota was hit — disallowed model, requests/minute, daily tokens, or budget period exceeded |
| `billing_error` | 403 | Wallet/credit-balance failure — insufficient credits or no wallet on the workspace |
| `server_error` | 5xx | Upstream provider failure (often retried by fallback chain) |

## Error IDs

Every error response includes `x-request-id`. Include it when reporting issues — our support can look up the full request/response in seconds.

## Retrying

Retryable — with exponential backoff and jitter, **and only where repeating the
call cannot be charged twice**: a `GET`, or a `POST` you sent an
`Idempotency-Key` on (`/v1/files` and `/v1/pipelines/runs` are the only two that
honour one):
- 409 `upload_in_progress` — file writes for one workspace are serialised; we already
  wait up to 10s for the lock, so this means the workspace was busy for longer than that
- 500, 503

Not retryable:
- 403 `rate_limit_exceeded` — a 60-second sliding window that counts refused requests
  too, so an early retry extends it. Wait out the window; see
  [Rate limits](/api-reference/rate-limits)
- 403 `daily_tokens_exceeded` — nothing to wait out before UTC midnight
- 403 `insufficient_credits` — top up first
- Any error whose body carries a `job_id` — including 504 `job_timeout` and
  500 `artifact_unreadable`. The work exists server-side and is already billed:
  collect it from `GET /v1/images/jobs/{job_id}` instead of paying for a second one
- Every other 4xx — they're your client's fault; fix the request
- A 5xx on a billed `POST` with no idempotency key. Distinct upstream failures —
  some of them *after* your balance was debited — collapse into the same generic
  500, so a blind retry can pay twice

Our fallback chains already retry server-side for you if configured — see [Fallbacks](/workspaces/fallback-chains).
